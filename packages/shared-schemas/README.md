# Public-ledger shared schemas v0.2.0

This draft replaces the archived v0.1 proof-input envelope. It describes public
transaction intents, signed RFQs, canonical accounting events and withdrawal
records for the Open Innovation plan. It is not a deployed contract ABI, token
standard conformance claim or cryptographic signature serializer.

`public-ledger.schema.json` is generated by `build_schema.py`; run it with
`--check` to check reproducibility. All objects reject extra fields. The `.invalid`
schema ID is an identifier, not a network dependency. No API credentials are used.
`validate.py` additionally enforces u128/u64 bounds, unique asset IDs per batch,
four-series vault baskets, matching quote/transaction domains and impossible
withdrawal-refund combinations. `loads_strict` rejects duplicate JSON keys and
nonfinite numbers before validation.

Amounts, exact public balance deltas and public account IDs are intentional.
Assets are COLLATERAL, P/N plus series ID, or VAULT_SHARE plus vault ID. Events
use CREDIT/DEBIT with unsigned amounts; sum them per asset and accounting bucket.
`ledger_id` distinguishes a series reserve, vault, withdrawal ticket or other
ledger scope inside that bucket; its canonical derivation is still to be pinned.
Events may be informational with no deltas. Every state-changing implementation
must emit its full audited deltas; schema validity alone does not ensure that.

Quotes are all-or-nothing exact amounts with an Ed25519 registered-key candidate,
nonce/cancellation epoch, explicit network/contract and public fees. A quote is
not a reservation guarantee. G5 pins the signature bytes and key registry in
[MARKET](../../docs/MARKET.md); arbitrary JSON serialization is not a signing
format. Callbacks are intentionally absent from client transaction intents;
private on-chain callback authorization is mandatory.

Array maxima (8 quote legs, 9 vault basket assets, 32 event deltas) are draft
validation limits, not measured gas/storage budgets. At most four distinct
series plus collateral may appear in a vault basket. Timestamps and nonce
counters use u64; monetary amounts use u128. Mainnet domains are rejected.
Schema v0.1/proof/nullifier/opening fields are rejected rather than reinterpreted.

The G3/G5 ABI, asset IDs, key management, scoped permissions, ledger log framing
and bounded views are in [contracts/README](../../contracts/README.md).
Vault roll proposals, non-demo oracle records, receiver/resolver interfaces and
the full G7 SDK remain future work. Current state,
block time, balances, signature authenticity, fees, economic caps, receipt
outcomes and predecessor authorization must be checked by contracts. Passing this
offline validator never authorizes a debit, finalizes a price or verifies a payout.
Receipt IDs are checked for base58 shape only; the eventual SDK must decode and
correlate actual receipt IDs and results rather than trusting this field.

G3 adds six internal-ledger client intents (storage deposit/release/unregister,
ticket cleanup, dust release, scoped pause) and their event types. SUPPLY is a
separate mirror of issued P/N, not another owned balance; OPERATING identifies the
bootstrap allocation. Actual G3 events are validated against this schema by the
Sandbox runner. The normalized withdrawal record above is not the raw core ticket
view: core ticket IDs are decimal u64 strings, receipt correlation comes from
recorded execution outcomes, and closing a terminal ticket removes its state.
The implemented ABI and cap rules are documented in `contracts/README.md`;
protocol-types strictly decodes canonical decimal strings. Vault intents remain
drafts; G5 implements native/P/N quotes with a stricter four-leg-per-side cap.

G4 adds `oracle.schema.json`, generated by `build_oracle_schema.py` through the
same `build_schema.py` entry point. It validates demo registration terms, source
evidence and actual `hedgeveil_oracle` receipt envelopes. Contract methods enforce
semantic bounds, predecessor authorization, evidence hashes and deadlines; JSON
Schema alone does not. Canonical commitment JSON sorts all nested keys explicitly
and uses UTF-8 strings with decimal-string amounts/timestamps. This format is for
G4 hashes, not the G5 binary RFQ signing format.

G4 events contain aggregate bond-accounting totals and a state hash, not G3's
per-account deltas. Complete G7 indexing still needs those account-level updates
and receipt correlation; no full event-replay indexer conformance is claimed.
Case views preserve accepted samples, proposal/challenge inputs and final evidence.

G5 adds `pair_quote`, five client intents (pair matching, key registration/revocation,
epoch advancement and market pause) and corresponding ledger event types. There
are 23 intent variants. `match_pair` carries `pair_quote` as its normalized `quote`
argument. Semantic validation checks positive complementary contributions and
matching domains. Contract limits additionally enforce current epoch, nonce
0..255, fee cap and live funding; a schema-valid signature string is not verified.
The separate `hedgeveil_rfq` fill audit envelope identifies the signed digest and
is reconciled by the Sandbox harness; it is not a canonical ledger-event envelope.
